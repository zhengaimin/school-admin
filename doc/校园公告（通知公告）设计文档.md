# 校园公告（通知公告）设计文档

## 1. 背景

本文以“对标系统（截图）”的通知公告能力作为产品模板，结合本仓库现状，给出一套可落地的“校园公告”跨端设计。

对标系统通常具备的能力（模板）：

- 管理后台有“通知公告”页面（列表/新增/发布/撤回/图片上传/选择受众与范围）。
- 话机/电子班牌设备侧可通过 open 接口拉取公告（例如 `getGhControlData` 的 `noticeList`）。

本仓库与公告相关的现状：

- GH 设备侧：`internal/service/gh_device.go:GetGhControlData` 已支持 `controlType=noticeList`，但当前为硬编码示例；数据结构在 `internal/schema/open/gh_device.go:GhNotice/GhNoticeFile`。
- 小程序侧：本期仅做“公告列表/详情展示”，不设计任何提醒推送能力。

“校园公告”定义：后台发布 -> 多端按受众范围展示（全校/年级/班级）。

## 2. 目标

- 后台支持创建/编辑/发布/撤回校园公告，支持图片附件。
- 支持受众范围：家长、校园公共（电子班牌/话机公告位）。（当前系统无“老师端”，本设计不包含老师端投放与展示）
- 支持范围粒度：全校、年级、班级。（一期暂不支持“指定人/指定学生”）
- 多端数据闭环：
  - 后台管理系统：公告管理与投放配置。
  - APK 首页：公告轮播/列表数据。
  - 家长小程序端：公告列表/详情。
- 与现有仓库结构对齐（`internal/` 业务逻辑、`model/store/controller/router/schema` 分层清晰）。

非目标（一期不做或可选）：

- 公告“已读/未读”体系（本期不做，不建已读表；如后续确有需要再补充）。
- 复杂灰度/AB/多渠道策略（后续可扩展）。

## 3. 术语与约定

- 公告（Announcement）：一条可跨端展示的内容实体（标题、正文、图片、发布时间）。
- 受众（Audience）：公告面向的人群类型（家长/公共屏）。
- 范围（Scope）：公告的投放范围（全校/年级/班级）。
- 展示端（Channel/Scene）：公告呈现位置（后台、APK首页、小程序）。

## 4. 现状梳理（基于当前仓库）

- 设备侧控制数据：`internal/service/gh_device.go:GetGhControlData` 已支持 `controlType=noticeList`，但目前返回硬编码示例数据；数据结构在 `internal/schema/open/gh_device.go:GhNotice/GhNoticeFile`。
- 通知系统：`internal/model/notification.go`、`internal/store/notification.go` 属于“用户通知”模型（user_id + status 已读），不适合承载“按范围投放的校园公告”。
- 文件/图片：已有 `files` 表与文件服务（`internal/service/file.go`），可复用作公告图片附件。

结论：校园公告建议作为独立领域建模，不复用 `notifications`。

## 5. 总体方案

核心思路：新增“公告实体 + 受众/范围规则”，并为不同端提供不同的查询口径。

- 后台创建公告并配置投放规则（受众+范围+展示端）。
- 设备/APP/小程序按自身上下文（school/grade/class/student/family）动态过滤可见公告。
- 对话机（GH）端：将 `noticeList` 从硬编码切换为查询公告并映射到 `GhNotice/GhNoticeFile`。

## 6. 数据模型设计（建议）

> 字段类型以 PostgreSQL 为主；具体命名可按现有仓库风格调整。

### 6.1 公告表：`announcements`

- `id` (int64，自增主键；与现有 `School/Student/Device` 等模型一致)
- `tenant_id` (int64；与现有模型一致)
- `school_id` (int64，公告归属学校)
- `title` (varchar(200))
- `content` (text)
- `images` (text，可选；JSON 数组字符串，存完整图片 URL，例如 `["https://xx/a.jpg","https://xx/b.jpg"]`)
- `status` (int：1=已发布，2=已下架)
- `publish_at` (timestamp，发布时间；发布时写入，用于多端展示与排序)
- `created_by` (bigint/varchar)
- `created_at/updated_at`

约束建议：

- `tenant_id + school_id + publish_at` 建索引，便于按校查询。

### 6.2 投放规则表：`announcement_targets`

一条公告可对应多条投放规则（“受众 + 范围”）。

- `id`
- `announcement_id`
- `audience_type`：
  - `PARENT`（家长）
  - `PUBLIC_SCREEN`（校园公共屏：电子班牌/话机公告位）
- `scope_type`：
  - `SCHOOL_ALL`
  - `GRADE`
  - `CLASS`
- `scope_id`（grade_id/class_id；`SCHOOL_ALL` 可为 0）
- `extra` (jsonb，可选：例如“展示端scene白名单/黑名单、轮播时长”等)
- `created_at`

索引建议：

- `(audience_type, scope_type, scope_id)` 联合索引（过滤可见公告的核心条件）。
- `announcement_id` 索引（JOIN/级联删除）。

图片存储说明（为什么不用附件表）：

- 对标系统场景中公告图片主要用于展示，业务上只需要“图片 URL 列表”。
- 参考现有 `internal/model/school.go` 的 `Photos` 设计：用 `text` 字段保存 JSON 数组字符串，并提供 `SetXxx/GetXxx` 方法序列化/反序列化。
- 为避免 APK/设备端“无法推导文件路径/相对路径”的问题，建议保存“完整可访问 URL”（由后台上传后返回的 URL 或静态资源 URL）。

## 7. 多端接口设计（建议）

### 7.1 后台管理端（Admin）

路径风格参考现有 `internal/router/admin.go`。

- `POST /admin/announcements`：创建公告（默认已下架状态 `status=2`）
- `PUT /admin/announcements/:id`：编辑公告
- `GET /admin/announcements`：列表（支持 status、title、time range、schoolId）
- `GET /admin/announcements/:id`：详情（含 targets/images）
- `POST /admin/announcements/publish`：批量发布（body 传 ids 数组）
- `POST /admin/announcements/revoke`：批量撤回（body 传 ids 数组）
- `DELETE /admin/announcements`：批量删除（body 传 ids 数组，仅已下架状态可删）

创建/编辑请求建议结构（示例）：

```json
{
  "schoolId": 1,
  "title": "放假通知",
  "content": "……",
  "targets": [
    { "audienceType": "PARENT", "scopeType": "CLASS", "scopeId": 1001 },
    { "audienceType": "PUBLIC_SCREEN", "scopeType": "SCHOOL_ALL", "scopeId": 0 }
  ],
  "images": ["https://xx/a.jpg", "https://xx/b.jpg"]
}
```

### 7.2 设备侧与 APK 侧（复用 GH 三个接口，不新增 open 接口）

现有入口（GH 三个接口）：

- `POST /ghAppController/getData`（数据获取）
- `POST /ghAppController/submitData`（数据提交）
- `POST /ghAppController/result`（命令反馈）

其中，公告统一走：

- `POST /ghAppController/getData`
  - `operation = getGhControlData`
  - `controlType = noticeList`（对应 `internal/constant/device.go:CONTROL_TYPE_NOTICE_LIST`）
  - 响应结构：`internal/schema/open/gh_device.go:GhControlDataResp` 的 `List1/List2`

改造建议：

- 将 `noticeList` 的硬编码替换为 DB 查询：
  - 通过设备定位学校（仓库已有 `getSchoolInfoByDevice`）
  - 支持公共屏公告拉取（同一个接口，不新增接口）：

**场景：APK/班牌首页（公共屏公告）**

- 触发条件：不传 `userUuid`
- 过滤条件：
  - `status=1`（已发布）
  - `publish_at <= now`
  - `audience_type = PUBLIC_SCREEN`
  - `scope` 命中：`SCHOOL_ALL`

说明（一期约束）：

- 当前仓库 `Device/DeviceGroup` 模型只有 `school_id`（没有设备绑定 `grade_id/class_id` 的字段），因此一期公共屏公告只支持“全校”投放（`SCHOOL_ALL`）。
- 若后续确需支持公共屏按年级/班级投放，需要补齐“设备上下文（年级/班级）”的数据来源（例如给 `device_groups` 增字段，或用现有 tag/关系表承载），并同步调整过滤条件与缓存 key。
- 映射到 GH 协议：
  - `GhNotice.ImageTextUuid <- announcement.id`（建议直接用字符串化的 announcement.id）
  - `GhNotice.SourceType <- "校园公告"`（或固定为一个常量，保证“唯一说明”字段稳定）
  - `GhNotice.BillType <- "NOTICE_ANNOUNCEMENT"`（固定值）
  - `GhNotice.Title <- title`
  - `GhNotice.Text <- content`（如需截断，设备端再做；服务端不建议硬截断）
  - `GhNotice.PushTime <- publish_at`（格式：`2006-01-02 15:04:05`）
  - `GhNotice.TextSize <- 16`（默认值，除非后续要做后台可配置）
  - `GhNotice.TextColor <- "#00ff00"`（默认值，除非后续要做后台可配置）
  - `GhNoticeFile`（按图片逐条生成列表；结构见 `internal/schema/open/gh_device.go:GhNoticeFile`）：
    - `ImageTextUuid <- announcement.id`（同上）
    - `FileUrl <- announcements.images[n]`
    - `FileUuid <- md5(fileUrl)`（或直接使用 url，但建议 md5 固定长度）
    - `ImageTextListUuid <- md5(announcement.id + "|" + fileUrl)`（同一公告下每张图唯一）
    - `CreationDate <- publish_at`（格式：`2006-01-02 15:04:05`）

### 7.3 家长小程序端

目的：公告列表/详情。

建议走现有 `/api` 体系（见 `internal/router/api.go`）：

- `GET /api/announcements`：列表
- `GET /api/announcements/:id`：详情（含图片）

## 8. 后台页面/交互设计（建议）

页面：`信息发布 / 通知公告`（截图所示）

- 列表字段：
  - 标题、发布时间、发布状态、操作（编辑/删除/发布/撤回）
- 新增/编辑弹窗（与截图三段式一致）：
  1. 标题、正文、图片
  2. 通知对象（家长/班牌/公话）
  3. 范围选择（全校/年级/班级/指定人），支持穿梭框或树形选择
- 发布校验：
  - 必填：标题、正文、至少一条 targets
  - 发布时间由发布动作写入，不允许手动改为未来时间（如确有定时发布需求，二期再做）

## 9. 缓存与同步策略（建议）

- 设备/APK 端拉取频繁：建议按 `school_id + audience_type + scene + (scope_context)` 做 Redis 缓存（TTL 30~120s）。
  - `scope_context`：公共屏一期仅 `school_id` 即可；若后续支持公共屏按年级/班级投放，再加入 `grade_id/class_id`。
- 发布/撤回时主动删除相关缓存 key（或维护 `school_announcement_version` 版本号，客户端带版本做增量）。

## 10. 落地建议（分期）

1. 第一期（最小可用闭环）

- 表结构：`announcements/announcement_targets`
- 后台 CRUD + 发布/撤回
- GH 端 `noticeList` 从硬编码改为真实公告查询（公共屏公告）
- 小程序端列表/详情

2. 第二期（增强）

- 更细粒度投放（例如：指定人群、更多展示端 scene 控制）
- 公告浏览数统计、导出
- 更复杂的 scene 控制（不同端不同内容）
