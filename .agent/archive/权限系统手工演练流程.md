# 权限系统手工演练流程

> 本流程以后台提供的 `.agent/archive/权限系统-测试指南.md` 为验收标准。文中的“代理商”对应后端 `AGENT` 租户；除接口、字段和数据记录外，页面及测试沟通统一使用“代理商”，不向普通用户展示“租户”“parent_id”等技术术语。

## 1. 演练目标与判定原则

### 1.1 演练目标

按真实使用顺序完成并验证：

```text
系统初始化平台根租户
-> SUPER 创建唯一的平台运营方角色和账号
-> 全量平台管理员创建代理商、学校和代理商管理员
-> 代理商管理员创建部门、业务角色和业务人员
-> 为平台账号分配代理商范围，为业务人员分配学校范围
-> 验证功能权限、数据权限、实时生效和角色越级保护
```

本轮必须覆盖以下能力：

- 平台开通代理商并维护学校；
- 平台为代理商创建管理员；
- 代理商创建业务角色和业务人员；
- 功能权限控制“能做什么”；
- 数据权限控制“能管理哪些代理商和学校”；
- 前端传入的筛选参数不能扩大后端授权范围；
- 用户、角色、权限和数据范围变更后及时生效。

### 1.2 单次请求的放行条件

```text
登录认证通过
+ 路由权限码通过
+ 角色层级检查通过
+ 代理商/学校数据范围通过
= 允许操作
```

前端隐藏菜单或按钮只能改善交互，不能作为权限通过的证据。所有拒绝类用例都必须使用当前账号的 token 直接调用接口，确认后端结果。

### 1.3 角色层级与默认最大范围

| RoleLevel  | 页面名称   | 典型用户     | 默认最大范围               |
| ---------- | ---------- | ------------ | -------------------------- |
| `super`    | 超级       | 超级管理员   | 全平台                     |
| `platform` | 平台运营方 | 平台管理员   | 全平台，可配置代理商白名单 |
| `agent`    | 代理商     | 代理商管理员 | 本代理商                   |
| `custom`   | 业务员     | 业务人员     | 指定学校                   |

角色只能向下创建或分配：

| 当前账号层级 | 允许创建或分配                | 必须拒绝                     |
| ------------ | ----------------------------- | ---------------------------- |
| `super`      | `platform`、`agent`、`custom` | 将 `super` 分配给其他用户    |
| `platform`   | `agent`、`custom`             | `platform`、`super`          |
| `agent`      | `custom`                      | `agent`、`platform`、`super` |
| `custom`     | 无                            | 所有角色级别                 |

因此，唯一的 `platform` 角色和用户必须由 `SUPER` 创建。平台管理员不能再创建或分配同级 `platform` 用户。

### 1.4 测试证据

每个接口用例至少记录：

| 记录项   | 内容                                      |
| -------- | ----------------------------------------- |
| 操作账号 | 账号代号、用户名、用户 ID、角色 ID        |
| 目标数据 | 代理商 ID、学校 ID、目标用户或角色 ID     |
| 请求     | HTTP 方法、路径、关键参数                 |
| 响应     | HTTP 状态、业务码、响应消息、返回数据摘要 |
| 结果     | 通过、失败或阻塞                          |

“拒绝或按不存在处理”的用例，只要没有返回越权数据即可通过；不得把所有数据越权结果都固定要求为 403。

| 测试状态代号         | 实体账号      | 角色权限状态                 | 数据范围状态            | 用途             |
| -------------------- | ------------- | ---------------------------- | ----------------------- | ---------------- |

### 2.5 数据范围语义

| 配置                  | 当前设计语义                           |
| --------------------- | -------------------------------------- |
| `ALL`                 | 当前角色层级允许的全部数据             |
| `TENANT + [代理商ID]` | 仅指定代理商                           |
| `TENANT + []`         | 只能访问用户自己的租户，不是全部代理商 |
| `SCHOOL + [学校ID]`   | 仅指定学校                             |
| `SCHOOL + []`         | 本代理商全部学校，不是无学校权限       |

空列表语义必须单独测试。前端配置页应明确展示对应含义，不能用“未选择任何数据”误导操作人员。

## 3. 第一级：SUPER 初始化唯一平台运营方

### 3.1 确认平台根租户

平台根租户由系统初始化创建，不通过普通后台接口创建。记录实际数据：

| 项目          | 实际值          |
| ------------- | --------------- |
| `PLATFORM_ID` |                 |
| `code`        | 应为 `platform` |
| `type`        | 应为 `PLATFORM` |
| `parent_id`   | 应为 `NULL`     |

### 3.2 创建唯一平台运营方角色

使用 `SUPER` 进入“权限模块 -> 角色管理 -> 新增角色”。

| 字段     | 内容                                           |
| -------- | ---------------------------------------------- |
| 角色名称 | 云帆平台管理员                                 |
| 账号类型 | 平台运营方（`platform`）                       |
| 描述     | 负责代理商、学校、角色、账号和全部下级权限管理 |
| 功能权限 | 平台运营方权限树全部模块、全部权限             |

创建成功后记录 `PLATFORM_ROLE_ID`。本流程不再创建其他 `platform` 角色；白名单和无代理商权限码用例均通过临时调整该角色或账号的数据范围完成。

### 3.3 创建唯一平台运营方账号

仍使用 `SUPER`，进入“用户管理 -> 平台用户 -> 新增用户”，对应接口：

```http

```

| 字段     | 内容                           |
| -------- | ------------------------------ |
| 用户名   | `yunfanAdmin`                  |
| 初始密码 | `111111`                       |
| 真实姓名 | 陆闻川                         |
| 手机号   | 19900005101                    |
| 邮箱     | lu.wenchuan@yunfan.example.com |
| 账号类型 | 平台运营方（`platform`）       |
| 角色     | 云帆平台管理员                 |
| 所属租户 | 平台根租户 `PLATFORM_ID`       |
| 状态     | 启用                           |

前端不能把平台运营方绑定到代理商 A 或 B。创建成功后记录接口返回的 `PLATFORM_USER_ID`、实际用户名和 `PLATFORM_ROLE_ID`。

### 3.4 设置平台账号基线

使用 `SUPER` 设置平台账号的全量数据范围：

```http
PUT /admin/data-scopes/users/{PLATFORM_USER_ID}
```

```json
{
  "scopeType": "ALL",
  "tenantIds": [],
  "schoolIds": []
}
```

重新查询该用户的数据权限，确认 `scopeType=ALL`。随后使用 `yunfanAdmin / 111111` 登录，确认可以进入代理商、学校、角色和用户管理页面。

该状态记为 `PLATFORM_ALL`，是平台账号执行创建、维护和清理操作时必须恢复的基线。

### 3.5 初始化验收

- [ ] 系统中只有一个平台运营方角色“云帆平台管理员”。
- [ ] 系统中只有一个平台运营方账号 `yunfanAdmin`。
- [ ] 角色的 `roleLevel=platform`，账号属于平台根租户。
- [ ] `SUPER` 不能创建或分配另一个 `super` 用户。

- [ ] 已记录 `PLATFORM_ROLE_ID` 和 `PLATFORM_USER_ID`。
- [ ] 平台账号的数据范围已复核为 `ALL`。

预期：可以看到全部有权管理的代理商，包括 A、B。

### 7.2 全量平台管理员

确认 `yunfanAdmin` 的数据范围为 `ALL`，且“云帆平台管理员”角色保留全部 `tenant:*` 权限。该状态记为 `PLATFORM_ALL`。

使用 `yunfanAdmin` 调用 `GET /admin/tenants`。

预期：拥有 `tenant:list`，可以看到代理商 A、B。

### 7.3 切换为代理商白名单状态

保持“云帆平台管理员”角色的全部权限不变，使用 `SUPER` 临时修改同一个 `yunfanAdmin` 的数据范围：

```http
PUT /admin/data-scopes/users/{PLATFORM_USER_ID}
```

```json
{
  "scopeType": "TENANT",
  "tenantIds": ["AGENT_A_ID"],
  "schoolIds": []
}
```

重新查询数据权限，确认返回 `TENANT + [AGENT_A_ID]`。此时同一个账号的测试状态记为 `PLATFORM_LIMITED`，继续使用其原 token 验证数据范围是否及时生效：

| 操作              | 请求                                 | 预期               |
| ----------------- | ------------------------------------ | ------------------ |
| 查询代理商列表    | `GET /admin/tenants`                 | 只返回代理商 A     |
| 查询代理商 A 详情 | `GET /admin/tenants/{AGENT_A_ID}`    | 成功               |
| 查询代理商 B 详情 | `GET /admin/tenants/{AGENT_B_ID}`    | 拒绝或按不存在处理 |
| 修改代理商 A      | `PUT /admin/tenants/{AGENT_A_ID}`    | 成功               |
| 修改代理商 B      | `PUT /admin/tenants/{AGENT_B_ID}`    | 拒绝               |
| 删除代理商 B      | `DELETE /admin/tenants/{AGENT_B_ID}` | 拒绝，且 B 仍存在  |

修改代理商 A 时只改一个可恢复字段，验证后立即恢复。删除测试只能以 B 为目标，并在请求后确认 B 及其学校未被删除。

继续使用当前 `PLATFORM_LIMITED` 状态尝试传入代理商 B 或平台根租户条件：

```http
GET /admin/tenants?parentId={PLATFORM_ID}
GET /admin/tenants?tenantId={AGENT_B_ID}
GET /admin/tenants/{AGENT_B_ID}
```

预期：任何前端参数都不能扩大后端授权范围，列表始终不能返回 B 的数据，详情不能返回 B 的内容。

### 7.4 切换为无代理商权限码状态

先使用 `SUPER` 把 `yunfanAdmin` 的数据范围恢复为 `ALL`，再编辑唯一的“云帆平台管理员”角色：

1. 保存当前完整权限 ID 列表，作为恢复依据；
2. 临时移除 `tenant:list`、`tenant:create`、`tenant:update`、`tenant:delete`；
3. 其他角色权限保持不变；
4. 保存后不要重新登录，继续使用 `yunfanAdmin` 的原 token。

此时同一个账号的测试状态记为 `PLATFORM_NO_TENANT`：

| 接口                                 | 缺少权限        | 预期                          |
| ------------------------------------ | --------------- | ----------------------------- |
| `GET /admin/tenants`                 | `tenant:list`   | 403 `无操作权限`              |
| `POST /admin/tenants`                | `tenant:create` | 403 `无操作权限`              |
| `PUT /admin/tenants/{AGENT_A_ID}`    | `tenant:update` | 403 `无操作权限`              |
| `DELETE /admin/tenants/{AGENT_A_ID}` | `tenant:delete` | 403 `无操作权限`，且 A 仍存在 |

该用例同时验证角色权限修改对原 token 及时生效。四项完成后，使用 `SUPER` 恢复保存的完整权限 ID 列表。

### 7.5 恢复平台账号基线

使用 `SUPER` 复核同一个 `yunfanAdmin`：

- [ ] 数据范围恢复为 `ALL`；
- [ ] “云帆平台管理员”角色恢复全部 `tenant:*` 权限；
- [ ] 原 token 或重新登录后的 token 可以再次查询 A、B；
- [ ] 系统中仍然只有一个平台运营方角色和一个平台运营方账号。

恢复完成后，该账号重新处于 `PLATFORM_ALL` 状态。

### 7.6 代理商管理员

使用 `AGENT_A_ADMIN` 调用代理商列表、详情、创建、修改和删除接口。

预期：全部拒绝。该账号只应在登录上下文中知道自己的代理商，不应进入“代理商管理”页面。

## 8. 功能权限专项测试

### 8.1 缺少权限码

复核第 7.4 节 `PLATFORM_NO_TENANT` 状态下调用 `GET /admin/tenants` 的结果，并使用 `OPERATOR_A1` 调用设备删除接口。

预期：HTTP 403，响应消息为 `无操作权限`。

仅检查页面不显示按钮不能判定通过，必须直接调用接口。

### 8.2 未配置权限的受保护路由

测试前由后台提供一个已受登录中间件保护、但未在 `internal/middleware/permission_config.go` 配置的实际路由：

| 项目     | 实际值 |
| -------- | ------ |
| 测试路由 |        |
| 操作账号 |        |

调用该路由，预期 HTTP 403，响应消息为 `接口未配置权限，访问被拒绝`。

如果后台未提供可测试路由，本项记录为“阻塞”，不得自行猜测路径或用 404 代替通过结果。

### 8.3 下级权限不能超过上级

使用 `AGENT_A_ADMIN` 更新“澄舟设备运维”角色，在请求中加入一个当前管理员自身没有的权限 ID。

预期：后端拒绝，角色权限不发生变化。不能通过创建或更新下级角色扩大权限。

### 8.4 权限修改实时生效

1. 使用 `OPERATOR_A1` 登录并取得 token；
2. 先使用该 token 成功修改学校 A1 的一条测试设备数据；
3. 使用 `AGENT_A_ADMIN` 从“澄舟设备运维”角色中移除 `device:update`；
4. 不重新登录，继续使用原 token 修改同一条设备数据；
5. 预期后端立即拒绝，无需等待 token 过期；
6. 测试后恢复 `device:update`，再次验证原 token 或重新登录后的 token 可以按预期操作。

## 9. 数据范围专项测试

### 9.1 跨代理商访问

使用 `AGENT_A_ADMIN` 或 `OPERATOR_A1` 访问代理商 B 的学校、设备、学生或支付数据。

预期：拒绝或查询不到，响应中不能包含代理商 B 的数据内容。

### 9.2 跨学校访问

使用 `OPERATOR_A1`：

| 目标数据 | 预期           |
| -------- | -------------- |
| 学校 A1  | 可以访问       |
| 学校 A2  | 拒绝或查询不到 |
| 学校 B1  | 拒绝或查询不到 |

分别测试列表筛选和详情接口。即使请求中主动传入 `schoolId=SCHOOL_A2_ID` 或 `schoolId=SCHOOL_B1_ID`，也不能返回越权数据。

### 9.3 空学校列表语义

临时把 `OPERATOR_A1` 设置为：

```json
{
  "scopeType": "SCHOOL",
  "tenantIds": [],
  "schoolIds": []
}
```

预期：可以访问代理商 A 的 A1、A2，仍不能访问代理商 B 的 B1。当前语义是“本代理商全部学校”，不是“无学校权限”。

验证后立即恢复 `SCHOOL + [SCHOOL_A1_ID]`。

### 9.4 空代理商列表语义

```json
  "schoolIds": []
}
```

预期：只能访问用户自己的平台根租户，不得把空列表解释为全部代理商；若代理商列表不展示平台根租户，则列表中不应出现 A、B。

验证后立即恢复 `ALL`，并确认 A、B 再次可见。

## 10. 状态和角色越级保护

### 10.1 禁用用户后原 token 立即失效

1. 使用 `OPERATOR_A1` 登录并取得 token；
2. 调用一个当前可成功访问的受保护接口并记录成功响应；
3. 使用 `AGENT_A_ADMIN` 禁用 `OPERATOR_A1`；
4. 不重新登录，使用原 token 再次调用同一接口；
5. 预期立即拒绝；
6. 测试后重新启用用户并确认可以正常登录。

### 10.2 禁用角色后原 token 立即失效

1. 使用 `OPERATOR_A1` 登录并取得 token；
2. 使用 `AGENT_A_ADMIN` 禁用“澄舟设备运维”角色；
3. 不重新登录，使用原 token 请求任意受保护接口；
4. 预期立即拒绝；
5. 测试后重新启用角色并确认账号恢复正常。

### 10.3 角色越级

前端应隐藏不允许的角色级别选项，同时必须篡改请求验证后端拒绝：

| 操作者                        | 尝试操作                                | 预期 |
| ----------------------------- | --------------------------------------- | ---- |
| `OPERATOR_A1`（`custom`）     | 创建或分配 `agent`                      | 拒绝 |
| `AGENT_A_ADMIN`（`agent`）    | 创建或分配 `agent`、`platform`、`super` | 拒绝 |
| `PLATFORM_USER`（`platform`） | 创建或分配 `platform`、`super`          | 拒绝 |
| `SUPER`（`super`）            | 将 `super` 分配给其他用户               | 拒绝 |

每次拒绝后重新查询目标角色或用户，确认没有产生脏数据。

## 11. 当前已知回归点

以下用例修复后必须全部通过：

1. 平台用户创建代理商后，代理商 `parent_id` 等于 `PLATFORM_ID`，不能为 `NULL`。
