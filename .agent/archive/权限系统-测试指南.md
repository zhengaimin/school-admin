# 权限系统操作与测试指南

本文档面向产品、测试、前端和后端人员，按真实使用顺序验证以下能力：

- 平台开通代理商并维护学校；
- 平台为代理商创建管理员；
- 代理商创建业务角色和业务人员；
- 功能权限控制“能做什么”；
- 数据权限控制“能管理哪些代理商和学校”；
- 后端不能被前端传入的筛选参数绕过。

整体规则参考：

- `docs/需求文档-商业概览版.md`
- `docs/apk/权限系统设计概述.md`
- `docs/apk/权限系统-操作指南.md`
- `internal/middleware/permission_config.go`

## 1. 业务模型

系统采用一个平台根租户、多个代理商租户的结构：

```text
平台运营方（PLATFORM）
├── 代理商 A（AGENT）
│   ├── 学校 A1
│   └── 学校 A2
└── 代理商 B（AGENT）
    └── 学校 B1
```

关键关系：

| 对象       | 归属字段                 | 含义                       |
| ---------- | ------------------------ | -------------------------- |
| 代理商租户 | `parent_id`              | 所属平台根租户 ID          |
| 学校       | `tenant_id`              | 所属代理商租户 ID          |
| 后台用户   | `tenant_id`              | 用户所属平台或代理商       |
| 业务数据   | `tenant_id`、`school_id` | 所属代理商及学校           |
| 公司部门   | `tenant_id`              | 所属代理商，仅用于人员归属 |

页面建议使用“代理商管理”，不要向普通用户展示“租户”“parent_id”等技术术语。

## 2. 权限判定原则

一次后台请求需要同时满足：

```text
登录认证通过
+ 路由权限码通过
+ 角色层级检查通过
+ 租户/学校数据范围通过
= 允许操作
```

前端可以传名称、状态、分页等搜索条件，但不能决定授权范围。可见代理商和学校必须由后端根据当前登录用户自动限定。

角色与默认范围：

| RoleLevel  | 典型用户     | 默认最大范围               |
| ---------- | ------------ | -------------------------- |
| `super`    | 超级管理员   | 全平台                     |
| `platform` | 平台管理员   | 全平台，可配置代理商白名单 |
| `agent`    | 代理商管理员 | 本代理商                   |
| `custom`   | 业务人员     | 指定学校                   |

## 3. 测试准备

### 3.1 测试账号

准备以下账号，实际 ID 记录在测试结果中：

| 账号代号             | 角色       | 数据范围              | 用途             |
| -------------------- | ---------- | --------------------- | ---------------- |
| `SUPER`              | `super`    | `ALL`                 | 全局管理和初始化 |
| `PLATFORM_ALL`       | `platform` | `ALL`                 | 验证平台全量管理 |
| `PLATFORM_LIMITED`   | `platform` | `TENANT + [代理商A]`  | 验证代理商白名单 |
| `PLATFORM_NO_TENANT` | `platform` | `ALL`，但无租户权限码 | 验证功能权限     |
| `AGENT_A_ADMIN`      | `agent`    | `TENANT`              | 代理商 A 管理员  |
| `AGENT_B_ADMIN`      | `agent`    | `TENANT`              | 代理商 B 管理员  |
| `OPERATOR_A1`        | `custom`   | `SCHOOL + [学校A1]`   | 验证学校范围     |

### 3.2 测试数据

```text
平台根租户：PLATFORM_ROOT

代理商 A：AGENT_A
├── 学校 A1：SCHOOL_A1
└── 学校 A2：SCHOOL_A2

代理商 B：AGENT_B
└── 学校 B1：SCHOOL_B1
```

建议每轮测试使用带时间标识的名称，避免名称唯一性冲突。

## 4. 完整操作流程

### 4.1 确认平台根租户

平台根租户由系统初始化创建，不通过普通后台接口创建。

预期数据：

```text
code = platform
type = PLATFORM
parent_id = NULL
```

记录平台租户 ID，后续记为 `PLATFORM_ID`。

### 4.2 创建代理商

使用 `SUPER` 或拥有 `tenant:create` 的平台管理员调用：

```http
POST /admin/tenants
```

```json
{
  "name": "权限测试代理商A",
  "contactName": "测试联系人A",
  "contactPhone": "13800000001",
  "address": "测试地址A"
}
```

使用相同方式创建代理商 B。

前端不传 `type`、`parentId` 或创建人租户 ID。后端应自动生成：

```text
type = AGENT
parent_id = PLATFORM_ID
```

验收点：

- 返回代理商 ID 和自动生成的编码；
- `type` 必须为 `AGENT`；
- `parent_id` 必须为平台根租户 ID；
- 不能将代理商创建成顶级租户；
- 代理商名称重复时创建失败。

### 4.3 创建学校

分别在代理商 A、B 下创建学校：

```http
POST /admin/schools
```

核心参数示例：

```json
{
  "name": "权限测试学校A1",
  "code": "AUTH_TEST_A1",
  "tenantId": 代理商A的ID,
  "address": "测试地址"
}
```

验收点：

- 学校 A1、A2 的 `tenant_id` 等于代理商 A；
- 学校 B1 的 `tenant_id` 等于代理商 B；
- 无权管理代理商 B 的用户不能在代理商 B 下创建学校。

### 4.4 创建代理商管理员

先查询代理商可用角色：

```http
GET /admin/roles?tenantId={AGENT_A_ID}&includeSystem=1
```

选择系统预置的 `agent_admin`，创建管理员账号：

```http
POST /admin/users
```

```json
{
  "username": "auth_agent_a_admin",
  "password": "测试初始密码",
  "realName": "代理商A管理员",
  "roleId": "agent_admin角色ID",
  "tenantId": "AGENT_A_ID",
  "status": 1
}
```

代理商管理员的有效数据范围应为本租户：

```json
{
  "scopeType": "TENANT",
  "tenantIds": [],
  "schoolIds": []
}
```

验收点：

- 管理员所属租户为代理商 A；
- 可以访问代理商 A 下的学校和业务数据；
- 不能访问代理商 B 的学校和业务数据；
- 不能创建或分配 `super`、`platform`、`agent` 级角色。

### 4.5 可选：创建公司部门

使用代理商 A 管理员创建部门：

```text
运营部
├── 设备运维组
└── 校园服务组
财务部
```

接口：

```http
POST /admin/org-departments
```

组织部门只表示人员归属，不应改变角色权限或学校范围。

### 4.6 创建业务角色

使用代理商 A 管理员获取可分配权限：

```http
GET /admin/permissions/modules
```

创建“设备运维”角色：

```http
POST /admin/roles
```

```json
{
  "name": "设备运维",
  "description": "查看和维护负责学校的设备",
  "roleType": "admin",
  "tenantId": "AGENT_A_ID",
  "roleLevel": "custom",
  "permissionIds": ["device:list对应ID", "device:update对应ID"]
}
```

验收点：

- 业务角色必须属于代理商 A；
- 角色级别为 `custom`；
- 不能分配代理商管理员自己没有的权限；
- 未选择 `device:delete` 时，使用该角色的用户不能删除设备。

### 4.7 创建业务人员并分配学校

建议先创建禁用账号，完成权限配置后再启用：

```http
POST /admin/users
```

```json
{
  "username": "auth_operator_a1",
  "password": "测试初始密码",
  "realName": "学校A1设备运维",
  "roleId": "设备运维角色ID",
  "tenantId": "AGENT_A_ID",
  "orgDepartmentId": "设备运维组ID",
  "status": 0
}
```

分配负责学校：

```http
PUT /admin/data-scopes/users/{OPERATOR_A1_ID}
```

```json
{
  "scopeType": "SCHOOL",
  "tenantIds": [],
  "schoolIds": ["SCHOOL_A1_ID"]
}
```

确认配置后启用账号。

验收点：

- 可以查看和修改学校 A1 的设备；
- 看不到学校 A2、B1 的设备；
- 没有 `device:delete` 时不能删除学校 A1 的设备；
- 调整组织部门不改变以上权限结果。

## 5. 租户可见性专项测试

### 5.1 超级管理员

使用 `SUPER` 调用：

```http
GET /admin/tenants
```

预期：可以看到全部有权管理的代理商，包括 A、B。

### 5.2 全量平台管理员

使用 `PLATFORM_ALL` 调用相同接口。

预期：拥有 `tenant:list` 时可以看到代理商 A、B。

### 5.3 受限平台管理员

给 `PLATFORM_LIMITED` 设置：

```json
{
  "scopeType": "TENANT",
  "tenantIds": ["AGENT_A_ID"],
  "schoolIds": []
}
```

验证：

| 操作              | 预期                           |
| ----------------- | ------------------------------ |
| 查询租户列表      | 只返回代理商 A                 |
| 查询代理商 A 详情 | 成功                           |
| 查询代理商 B 详情 | 拒绝或按不存在处理             |
| 修改代理商 A      | 成功，前提是有 `tenant:update` |
| 修改代理商 B      | 拒绝                           |
| 删除代理商 B      | 拒绝                           |

### 5.4 无权限码的平台管理员

使用缺少相应权限码的 `PLATFORM_NO_TENANT`：

| 接口                        | 缺少权限        | 预期 |
| --------------------------- | --------------- | ---- |
| `GET /admin/tenants`        | `tenant:list`   | 403  |
| `POST /admin/tenants`       | `tenant:create` | 403  |
| `PUT /admin/tenants/:id`    | `tenant:update` | 403  |
| `DELETE /admin/tenants/:id` | `tenant:delete` | 403  |

### 5.5 代理商管理员

使用 `AGENT_A_ADMIN` 调用租户列表、详情、创建、修改和删除接口。

预期：全部拒绝。代理商管理员只应在登录上下文中知道自己的代理商，不应进入“代理商管理”页面。

### 5.6 前端参数绕过

使用 `PLATFORM_LIMITED` 尝试传入代理商 B：

```http
GET /admin/tenants?parentId={PLATFORM_ID}
GET /admin/tenants?tenantId={AGENT_B_ID}
GET /admin/tenants/{AGENT_B_ID}
```

预期：前端参数不能扩大后端授权范围，始终不能看到代理商 B。

## 6. 功能权限专项测试

### 6.1 缺少权限码

使用没有目标权限码的用户调用相应接口。

预期：返回 403 `无操作权限`。

### 6.2 未配置路由

调用未在 `internal/middleware/permission_config.go` 配置的受保护路由。

预期：返回 403 `接口未配置权限，访问被拒绝`。

### 6.3 权限继承

代理商管理员创建或更新角色时，尝试加入自己没有的权限。

预期：拒绝，不能通过创建下级角色扩大权限。

### 6.4 权限修改实时生效

1. 业务人员登录并取得 token；
2. 从其角色中移除 `device:update`；
3. 使用原 token 再次修改设备。

预期：后端立即拒绝，无需等待 token 过期。

## 7. 数据范围专项测试

### 7.1 跨代理商访问

使用 `AGENT_A_ADMIN` 或 `OPERATOR_A1` 访问代理商 B 的学校、设备、学生或支付数据。

预期：拒绝或查询不到，不能返回代理商 B 的数据内容。

### 7.2 跨学校访问

使用 `OPERATOR_A1`：

| 数据    | 预期           |
| ------- | -------------- |
| 学校 A1 | 可以访问       |
| 学校 A2 | 拒绝或查询不到 |
| 学校 B1 | 拒绝或查询不到 |

### 7.3 空学校列表语义

设置：

```json
{
  "scopeType": "SCHOOL",
  "schoolIds": []
}
```

当前设计语义是“本代理商全部学校”，不是“无学校权限”。测试人员必须单独验证，前端应明确显示“本代理商全部学校”。

### 7.4 空租户列表语义

设置：

```json
{
  "scopeType": "TENANT",
  "tenantIds": []
}
```

当前设计语义是“只能访问自己的租户”。

## 8. 状态和越级保护

### 8.1 禁用用户

1. 用户登录并取得 token；
2. 管理员禁用该用户；
3. 使用原 token 请求任意受保护接口。

预期：立即拒绝。

### 8.2 禁用角色

1. 用户登录并取得 token；
2. 管理员禁用该用户的角色；
3. 使用原 token 请求任意受保护接口。

预期：立即拒绝。

### 8.3 角色越级

| 操作者     | 尝试操作                          | 预期 |
| ---------- | --------------------------------- | ---- |
| `custom`   | 创建或分配 `agent`                | 拒绝 |
| `agent`    | 创建或分配 `agent/platform/super` | 拒绝 |
| `platform` | 创建或分配 `platform/super`       | 拒绝 |
| `super`    | 把 `super` 分配给其他用户         | 拒绝 |

## 9. 当前已知回归点

以下用例用于验证待修复问题，修复前可能失败，修复后必须通过：

1. 平台用户创建代理商后，代理商 `parent_id` 应等于平台根租户 ID，不能为 `NULL`。
2. 配置 `TENANT + tenantIds` 的平台管理员，租户列表只能返回白名单代理商。
3. 受限平台管理员不能读取、修改或删除白名单之外的代理商。
4. 前端传入 `parentId`、目标租户 ID 或其他筛选条件，不能扩大数据范围。
5. 租户权限必须由后端上下文控制，不能依赖前端隐藏菜单。

## 10. 验收标准

全部满足后，权限主流程才算通过：

- 平台可以完成“创建代理商 → 创建学校 → 创建代理商管理员”；
- 代理商可以完成“创建部门 → 创建业务角色 → 创建业务人员 → 分配学校”；
- 代理商之间数据完全隔离；
- 同一代理商下可以按学校隔离业务人员；
- 功能权限与数据权限必须同时满足；
- 下级不能分配自己没有的权限或更高等级角色；
- 租户列表、详情、修改、删除均遵守平台管理员的代理商白名单；
- 任何前端参数都不能扩大后端授权范围；
- 用户、角色、权限和数据范围变更后，后端及时生效。
